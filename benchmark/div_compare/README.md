# LOD / 固定 32 次迭代除法对比

在项目根目录运行（使用现有 Vivado XSim 和真实乘法 IP）：

```cmd
benchmark\div_compare\run.cmd --lod-mhz 101.471 --fixed-mhz 101.864
```

默认固定随机种子，每个随机场景 256 对输入。对同一批程序分别运行 LOD 和固定
32 次迭代实现，`src/` 不变；仅在本目录 `build/both/lod` 和 `build/both/fixed32` 生成仿真
副本，差别只有 `leading_one_pos` 的计算。不是综合结果，Fmax 使用你传入的测量值。
以后更改除法架构，可用 `--mode current` 测试当时原始 RTL。

测试使用完整 `cpu_core`、一拍同步指令 ROM 和实际 RAM。覆盖 DIV/DIVU/REM/REMU：
8/16/32 位有符号与无符号随机数、最高位固定为 1、除零、零被除数、INT_MIN/-1、
连续除法、结果依赖、load/store/CSR forwarding，以及欧几里得 GCD 循环及分支。
每次逐项比对独立 Python 整数模型生成的寄存器写回、store 顺序和全部 8192 个 RAM
字；结果签名从数据地址 `0x1000` 开始，完成标志写到 `0x7ffc`。

输出整核周期、退休指令数、CPI、DIV/REM 提交数、除法停顿周期、实际迭代数、
EX 占用周期的平均/最小/最大值。EX 占用包含请求、准备、计算和完成交接周期，
固定 32 次迭代正常为 35 拍；总 cycles/div 还包含准备输入和保存结果等指令。
计时从释放复位到完成标志对应的 store 在 WB 退休，包含流水线启动开销。
这些是除法密集型合成负载，不是 CoreMark，也不表示普通应用的平均 CPI。

最终输出每种场景的周期加速比及考虑 Fmax 后的吞吐加速比（大于 1 表示 LOD 更快）：

`吞吐比 = (固定版本周期 / LOD 周期) × (LOD MHz / 固定版本 MHz)`

默认输出文件为 `build/both/results.csv`、`build/both/summary.json`；两种实现各场景的
日志和对应指令清单也在该目录下。其他 mode 的结果单独放在 `build/<mode>/`，
不覆盖 A/B 比较结果。随机数据及退休指令数一致，可直接对照。

```cmd
benchmark\div_compare\run.cmd --pairs 512 --seed 0x1234
benchmark\div_compare\run.cmd --mode current
```

32 位均匀随机数的最高有效位通常很高，LOD 平均只能少迭代约 1～2 次；小数、
逐渐缩小的余数与 GCD 更容易体现 LOD 的收益。不要只用均匀 32 位随机数作决定。

首次实测：默认种子及 256 对随机输入，两种实现共 22 次完整 CPU 仿真全部 PASS。
按 LOD 101.471 MHz、固定版 101.864 MHz 换算：

| 场景 | 固定版周期 | LOD 周期 | LOD 吞吐加速比 |
| --- | ---: | ---: | ---: |
| 8 位无符号随机数 | 19,985 | 7,293 | 2.730× |
| 16 位无符号随机数 | 19,985 | 11,269 | 1.767× |
| 32 位无符号均匀随机数 | 19,985 | 19,479 | 1.022× |
| 最高位恒为 1 | 19,985 | 19,985 | 0.996× |
| 除法/load/store/CSR 依赖 | 31,249 | 14,034 | 2.218× |
| 16 位欧几里得 GCD | 100,948 | 46,797 | 2.149× |

Fmax 来自两版实现记录；本脚本只仿真周期，不重新综合。后续修改源码或参数后，
以重新运行生成的 CSV 为准。
